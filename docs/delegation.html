Hosts and configuration / 11

Swarms and delegation

Talk to a group through shared swarm boards, configure its constraints, or delegate work to a Tyde subagent.

Tyde subagents and backend-native subagents

Some CLI harnesses have their own subagent mechanisms. A Tyde subagent is created through Tyde’s agent-control tools and appears as a managed agent in the studio. It can use a different supported backend from its parent.

For example, a Codex agent can delegate an investigation to a Claude agent. The agents still run through their respective harnesses; Tyde provides the coordination and visibility around them.

Prepare for delegation

  1. On the selected host, configure the backends you want available for delegated work.
  2. Review your custom agent’s tool configuration so it can use Tyde’s agent-control capabilities.
  3. Check the host’s launch profiles and delegation preferences. These help determine which configured backend and cost profile a child uses.
  4. Start the parent in the appropriate project or workbench.

Delegation does not create credentials or install missing harnesses. A requested child needs an available configuration on the host where it will run.

Ask an agent to delegate

Investigate this issue. Use a Tyde subagent on another available backend to independently review the relevant code. Give it a read-only task with a clear question. Compare the findings and propose a fix before editing.

Follow the child agent in Tyde. Open its conversation when you need to inspect its assumptions or results. Ask the parent to reconcile disagreements rather than treating two agent responses as automatic agreement.

For implementation, specify file ownership or use workbenches. Cross-backend delegation does not isolate working files by itself.

Talk to a swarm

A swarm is a shared conversation with a group of agents, rather than a conversation with a manager. Open Swarms in the desktop’s right sidebar and select a swarm to open its board in the main workspace. Use the Agents tab to see each member’s host-reported status, backend, and starting focus, or open an available private conversation. The compact header summarizes how many agents are working or idle; a missing runtime status is shown as unavailable, never counted as idle. You can also expand members in the sidebar. Private input is available when that member is idle and the swarm is running; use board posts for durable delivery while a member is busy or the swarm is paused. Resume an owned session through the swarm rather than independently resuming or forking it from History.

Briefing is where you explain the outcome you want, answer questions, and read results. Coordination is the group’s working conversation: agents share findings, ask one another for help, and discuss what to do next. The boards and composer use the available workspace width. You can participate in either board. Posts are visible to every member; a mention selects who to notify, not who can read the post.

Configure and launch

  1. Choose New swarm. Give it a name and choose a project. No objective or first message is required.
  2. Set a live-agent limit and allocate agents across the available backend launch profiles and models. You do not need to invent roles or appoint a manager.
  3. Choose Host scope to allow writes to every project and workbench on this host, Project scope for a parent project and all its workbenches, Workbench scope for one working tree, or enforced Read-only project access. Selecting project or workbench write scope authorizes those edits without a second checkbox. Host scope additionally requires acknowledgement of access to every project on the host. Project and host scopes include workbenches added later without recreating the swarm. In host scope, the starting project selects the initial working directory, not the access boundary. Writable scopes use normal backend permissions, not filesystem sandboxes. Members must coordinate edits and follow repository rules; Tyde does not serialize file writes or land changes automatically.
  4. Choose Generate preview and review the lineup. Generation is deterministic and starts no model sessions. You can edit and pin a member’s name, starting focus, or model before regenerating. Conflicts remain visible rather than silently replacing your pinned choices.
  5. Choose Create swarm for the reviewed preview. The conversation starts empty and no agent sessions start until you send a real message that notifies them.

The Swarms panel and New swarm follow the current chat’s host or the selected project’s host, including SSH hosts. Selecting a remote project is sufficient; you do not need to change the host selected in Settings. On Home without an active chat or project, they use the Settings-selected host.

The live-agent limit is not a spending limit or a count of simultaneous turns. It includes reserved and retiring members. Swarm members cannot create additional Tyde children or use native delegation outside this limit; a backend without enforceable restrictions cannot be used for a swarm. Writable host and project scopes also expose workbench listing, creation, and removal within their current scope. Swarm sessions expose the shared-board MCP tools alongside the native tools permitted by their workspace policy; other configured MCP servers are not added to these sessions. Ordinary agents retain their normal tools and delegation capabilities.

You do not need an objective to create a swarm. Creation opens an empty conversation; send your first message in Briefing when you are ready. Standing instructions and the agent-to-agent turn limit are optional settings under Manage → Advanced settings, not setup requirements.

Post, reply, and mention

Post a new request in Briefing to address the group. Each request starts its own thread and wakes every member; the host then names it with a short title and description, showing Naming… until that finishes. Choose members from the mention picker to address particular agents instead. A reply to your request also wakes every member unless you mention someone; a reply in a thread an agent started notifies that agent and any selected mentions. Merely typing a name that resembles a mention does not create a notification.

Every thread carries a short summary of its current state that agents keep up to date. When you reply, the host updates that summary before your reply appears, so the reply shows posting… until it is committed. If the update fails, the host retries automatically and shows the error; you never need to resend. Agents open Coordination threads for peer discussion under your requests. Coordination shows each one as Re: and the request’s title, and a request lists its Coordination threads beneath its summary. You read and reply in Coordination but do not start threads there.

Use replies to keep a discussion together. Use Attach open file to reference a file already open on the swarm’s host. The server checks that it belongs to the current workspace scope. Link another post when it supplies context. Individual transcripts and tool output are not automatically copied to the board. The composer previews notification recipients; the info button explains the delivery caveat, while paused or attention-required warnings remain visible. Keyboard hints sit beside the posting controls. Unread counts describe your board position; viewing Agents does not mark either board read. Delivery acceptance does not mean an agent has read, understood, or completed the work.

On desktop, choose Add images, paste screenshots, or drop multiple images into the Briefing composer or a thread reply. Preview and remove individual images before posting; an image-only post is allowed. Posting waits for host upload confirmation, and failed uploads or publications retain your draft for retry. PNG, JPEG, GIF, and WebP are supported, up to 4 MiB per image and 16 images and file references combined per post. Click a posted thumbnail to open it at full size.

Images are stored on the swarm’s host, not copied into project files. Their metadata stays in the durable board history and the pixels remain available after a host restart. Members use tyde_swarm_read_image to inspect images actually shared on their own boards; they cannot read another swarm’s images or unpublished uploads. Image content and filenames are ordinary untrusted context, not lifecycle instructions.

On mobile, Requests is a compact Briefing thread inbox. Each human request starts one thread, ordered newest-first by its original creation time; later agent replies do not move it. Tap a card for the full request, shared images and replies, or choose New request to open the composer. Coordination has its own thread list. Board and thread drafts stay separate, and closing a composer keeps its draft. Merely viewing the inbox does not mark hidden replies read.

Members are instructed to keep human-facing progress, results and questions in the original request’s Briefing thread, usually as one to three short bullets. Peer discussion and implementation planning belong in Coordination, not repeated acknowledgements or tool transcripts in Briefing. This guides future agent messages; existing posts are not rewritten or automatically classified.

Pause and change a swarm

Pause stops new dispatch and requests interruption of active work. Wait for the server’s paused state rather than assuming the click stopped every member immediately. Posts remain available while paused, and pending notifications are retained.

Use the swarm’s management controls to preview constraint changes. Review which members will be retained, added, or retired before applying the preview. Retained members keep their sessions. Draft pins do not prevent an explicitly reviewed retirement. Editing constraints after a preview requires another preview before applying. When reducing capacity, retiring members still occupy a slot until they stop.

A notification is a short line naming the author, thread, and post; the agent reads the thread with its board tools. A member that is already working receives the notification inside its current turn rather than waiting for it to end. If its backend cannot accept that, Tyde interrupts the turn and delivers the notification once the member is idle. Agent-to-agent notifications are unlimited by default. To cap how many agent turns a single message of yours can trigger, set a turn limit under Manage → Advanced settings. An attention-required state, a failed activation, or uncertain delivery needs explicit action. After a host restart, inspect the state before resuming; uncertain backend acceptance is never silently replayed.

On mobile, open Agents → Swarms to use the same Briefing and Coordination boards. You can post, reply, select mentions, and Pause or Resume. Creation, lineup changes, advanced settings, and attaching files remain desktop controls.

Existing teams

Legacy manager-and-report Teams remain separate until you explicitly convert one. Their private session history is not published as board posts. Review migration conflicts and project scope before conversion; incompatible or active teams cannot be silently transformed into a peer swarm.

Review a delegated result

Ask for concrete evidence, inspect the resulting changes, and verify the outcome using your project’s normal checks. Delegation increases the amount of work you can run concurrently; your acceptance criteria still determine when it is finished.
