Projects and agents / 04

Git changes and review comments

Inspect working changes and commits, add file or inline comments, and submit feedback to an agent.

Open a file, working change, or commit

Tyde connects review feedback to source code. You can inspect a file as it exists now, uncommitted changes, or changes from Git history.

What you needWhere to begin
Understand a fileOpen it from the file explorer. Use a file comment for feedback about the whole file, or an inline comment for a specific location.
Review current editsOpen the Git panel and select a file under Changes or Staged. Check the root and the diff before commenting.
Review committed workChoose Recent commits in the Git root header, select the commit or range, and open a changed file.

Read the change in context

Use unified or side-by-side diff views to compare old and new code. Expand context when you need to understand the surrounding function. A short diff can hide assumptions elsewhere in the file, so open the source when the change deserves a broader look.

For a multi-root project, confirm the repository as well as the filename. Review the actual changes rather than relying only on the agent’s explanation of them.

Add and submit review comments

  1. Find the relevant line or use Comment on file for feedback that applies to the file as a whole.
  2. Write the expected behavior and explain why the current change misses it.
  3. Open Review comments to read the collected feedback across roots.
  4. Choose the recipient under Send feedback to, then use Submit review when the review is ready.
  5. Read the agent’s response and review the revised code.

This returns an empty page when there are no results. Show an empty-state message with a way to clear the filters, so the user can recover without reloading.

A draft comment is not a submitted review. Collect your feedback, check its target, and submit it deliberately. If AI suggestions are pending, accept or reject them before submitting.

Configure review aspects

Run review opens the Review dialog. Select Inline for self-review guidance in the author's existing context, Single reviewer for one independent native context fork covering all selected aspects, or Review team for configured reviewer sources. Inline creates no reviewer agents or Review-panel findings and is guidance, not completion certification. Single reviewer inherits the author's backend and model without a separate model picker. Unsupported forks show an actionable reason rather than substituting a fresh agent.

Aspects are shared with Settings → Review. Use + Add aspect to enter a name and guidance; use the subtle Edit button on an existing row to change either. Changes persist under the same aspect ID and apply to later reviews without rewriting old findings. Each team source can be Fork current agent or a selected backend/model. Per aspect requires an explicit source for each selected aspect. Per reviewer assigns all aspects to each source. Every combination schedules one independent reviewer per source and aspect: three aspects and two sources schedule six agents. The server-provided preview shows actual assignments and counts. Forks still consume tokens.

Non-inline reviews retain the existing findings, inline accept/reject/navigation, Stop review and submit workflow. Completed reviewers are advisory, not approval. Failures are not clean reviews. Compatible follow-ups continue useful reviewer contexts; source/model or guidance changes invalidate affected contexts explicitly. Old Lite/Heavy selections are preserved and can be restored from saved selections; the previously selected mode migrates to its equivalent team layout.

Coding agents call tyde_preview_review to inspect configuration and capabilities, then tyde_review with a stable request_id and optional mode: "inline", "single_reviewer" or "review_team". Inline returns the selected guidance. Other modes wait for completion and return review IDs and counts; repeat the request ID to reattach after an interrupted wait. Use tyde_list_reviews and tyde_list_review_findings for IDs and summaries, tyde_read_review_finding for details, tyde_edit_review_comment to edit text without resolving, and tyde_resolve_review_findings for concrete batch resolutions. Audit history remains bounded and on demand through tyde_review_history. No extra mandatory review layers are introduced.

Stage and commit changes

The Git panel separates staged changes, unstaged changes, and untracked files. Stage the files you intend to include, inspect the staged result, and write a commit message describing the change. In a multi-root project, repeat this for each repository involved.

Use discard controls carefully: discarding a file’s working changes is different from rejecting a review suggestion. For parallel changes, workbenches give each task a separate working tree.
